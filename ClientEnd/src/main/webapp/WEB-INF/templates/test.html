RabbitMQ acts as a message broker or queue manager; rule of thumb: first in first out (FIFO). Functions: asynchrnous processing, decoupling complex services, balancing peak and trough periods.
The Pareto Principle, or the 80/20 rule, states that for most events, roughly 80% of the effects come from 20% of the cause.
With this, the number of needed machines is Query per Second during peak / QPS of each machine. Query per Second during peak can be estimated: (total Pageview * 80%) / (total seconds in a day * 20%) Terms: QPS: query per second PV: pageview / clicks UV: unique visitor PR: page rank (for importance) AMQP and JMS are two standards of messaging systems. AMQP, advanced message queuing protocol, is binary wire-level; where JMS, JavaMessage Service, operates at application level. RabbitMQ working mode: 1. one provider and one consumer (provider------queue------consumer) 2. one provider and multiple consumers; each message is only assigned to one single consumer (provider------queue------consumer1 ------consumer2) 3. one provider, one exchange, and multiple consumers: the provider connects to the exchange, and the exchange cannot store the messages but only handles how messages are being distributed according to three modes: (provider------exchange------queue------consumer1 ------queue------consumer2; so, the providers only need to declare the exchange and don't need to declare queues, good for decoupling; and only consumers declare queues and bind them to the exchange)   Fanout (broadcast),   Direct (to the queue with the specified routing key),   Topic (to the queues that matches routing wildcard patterns, where # matches 0 or more word(s), not character(s), and that * matches exactly 1 word) Process to create a RabbitMQ producer without an exchange (in main method): 1. create a ConnectionFactory, and set host, port, virtual host, username, and password 2. get new connection from the ConnectionFactory instance 3. create channel from the connection 4. declare a queue with the channel (parameters: String queue, Boolean durable, Boolean exclusive, Boolean autodelete, Map<String, Object> arguments) 5. basic publish the channel (parameters: String exchange, String routingKey, AMQP.BasicProperties props, byte[] body); this is to put a message into the queue 6. close the channel and connection The environment setup for the simple consumer is basically the same, except that basicPublish() needs to be changed to basicConsume(). We override handleDelivery method in new DefaultConsumer(channel){} to create a consumer instance.
Side note on Maven: For a depended Maven module to be successfully accessed by another module, this depended Maven module needs to have its classes properly put in packages, rather than directly under the src/main/java/ directory.
To use the fanout (publish/subscribe) mode, the provider needs to declare an exchange, and the consumers need to declare their own queues and bind the queue to the exchange using channel.queueBind(String queue, String exchange, String routingKey), instead of exchangeBind(x,x,x...). During the communication of publishing and consuming messages, messages can be lost because the exchange cannot store data, but we expect all the messages are delivered successfully and are never lost. To ensure reliable deliveries, there are two ways supported by RabbitMQ: confirm, and return. The chain of delivery: producer----->RabbitMQ_broker----->exchange----->queue----->consumer 1. When a producer sends a message to an exchange, it can request confirmation (acknowledgment) from RabbitMQ that the message has been successfully received and processed. (from the broker to the exchange) 2. When a producer sends a message to an exchange with mandatory routing (using channel.basicPublish with mandatory=true), RabbitMQ checks if the message can be routed to any queue. (from the exchange to the queue(s)) To enable in spring boot: 1. add the attributes to the connectionFactory bean: publisher-confirm="true" publisher-returns="true". 2.1 confirm callback code: 

// called no matter whether the delivery is successful
rabbitTemplate.setConfirmCallback(new RabbitTemplate.ConfirmCallback() {

	public void confirm(CorrelationData correlationData, Boolean ack, String cause) {
		// cause is the reason of success/failure
		if (ack) {
			// successfully received by the exchange
		} else {
			// failed
		}
	}
}

3. time to coverAndSend When a consumer acknowledges a message in a queue, the message will no longer exist in the queue, whereas when the consumer doesn't acknowledge the message, the message is returned to the queue: 1. change the acknowledge attribute of connectionFactory to "manual"; and add the listener below to the listener container 2. code: 

public class AckListener implements ChannelAwareMessageListener {
	@Override
	public void onMessage(Message message, Channel channel) throws Exception {
		// to acknowledge; deliveryTag can be retrieved from message.getMessageProperties().getDeliveryTag()
		channel.basicAck(long deliveryTag, Boolean multiple);

		// when accidents happen and we want to return the message to the queue
		channel.basicNack(long deliveryTag, Boolean multiple, Boolean requeue);
	}
}
By default, a consumer takes all messages at once; we can set the limit of messages it stages (prefetch, move from the queue before execution), to coordinate the capability of message handlers. To achieve this function, we only need to add the attribute "prefetch=a_number" in the tag "rabbit:listener-container". This setting restricts the number of messages in the "unacked/unacknowledged" status. (The status are: Ready--->Unacked--->consumed.) When a message is acknowledged (consumed), the consumer takes another one from the queue and keeps the number of messages in Unacked the same. 3 cases when a message becomes a dead letter: 1. a message arrives at a queue that is at its full capacity; 2. the consumer decided to basicNack/basicReject with requeue parameter set as false; 3. a message reaches its ttl limit There are 3 ways to deal with dead letters: 1. abandon 2. record dead letters for later analysis and handling 3. (most commonly adopted) push dead letters to DLX (dead letter exchange), where an application dedicated to handle dead letters can reach DLX receives messages from the originating queue, so we can treat the originating queue as the provider. Therefore, DLX needs to be bound to the provider queue by adding these entries to queue-arguments: x-dead-letter-exchange, and x-dead-letter-routing-key By default, a message is ready to be consumed once it arrives in the queue, but sometimes we want our message to be handled at a later time. However, RabbitMQ does NOT support delayed messages, but the accepted solution was to use a mix of message TTL and Deal Letter Exchange. The big idea is: provider---->exchange---->Queue with desired TTL and no consumer---->DLX (guaranteed to arrive here after TTL)---->Queue---->Consumer Configure RabbitMQ in springboot: Provider: with spring.rabbitmq.host/port/username/password/virtual-host configurations handy in application.yml (or .properties), create a configuration class (with @SpringBootConfiguration or @Configuration), with Exchange, Queue, and Binding beans created, where we use ExchangeBuilder, QueueBuilder, and BindingBuilder. Then ConnectionFactory, Connection, Channel, and RabbitTemplate instances will be automatically created for us to send messages. Consumer: with rabbitmq.host/port/username/password/virtual-host configurations handy in application.yml (or .properties), create a spring component class for listener, and include a method with Message param as its argument-this method should have @RabbitListener(queues = "queue_name") annotation.
